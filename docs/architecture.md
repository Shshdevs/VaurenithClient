# Архитектура VaurenithWeb

VaurenithWeb использует Clean Architecture с разделением ответственности между Domain, Application, Infrastructure, Presentation и App. Бизнес-логика остаётся независимой от React и конкретных способов работы с API или локальным хранением.

## Слои и расположение кода

- `src/domain` — предметные правила и типы без зависимостей от React, браузера и инфраструктуры. Сущности добавляются по необходимости и не копируют автоматически модели Backend.
- `src/application` — сценарии приложения и порты в `ports/`, которые определяют необходимые ему внешние возможности.
- `src/infrastructure` — технические реализации портов: API-клиенты, адаптеры внешних сервисов и локального хранения.
- `src/presentation` — страницы, маршруты и React-компоненты.
- `src/app` — composition root: создание инфраструктурных адаптеров, маршрутизатора и провайдеров приложения.
- `src/main.tsx` — точка входа приложения.

Текущая структура намеренно содержит только нужные файлы. Функциональные модули группируются по предметной области и добавляются по мере появления функций; заранее создавать пустые каталоги не нужно.

## Разрешённые зависимости

Направление импортов проверяется ESLint через `eslint-plugin-boundaries`.

| Слой-источник    | Разрешённые внутренние зависимости        |
| ---------------- | ----------------------------------------- |
| `domain`         | `domain`                                  |
| `application`    | `application`, `domain`                   |
| `infrastructure` | `infrastructure`, `application`, `domain` |
| `presentation`   | `presentation`, `application`, `domain`   |
| `app`            | все внутренние слои                       |
| `src/main.tsx`   | `app` и глобальные стили                  |

Дополнительные ограничения:

- `domain` не импортирует внешние runtime-пакеты.
- `application` и `infrastructure` не импортируют React, React Router или Vite.
- `presentation` не импортирует конкретные реализации из `infrastructure`; зависимости передаются через Application-порты.
- `app` соединяет слои, но не содержит бизнес-правил.
- Внутренние импорты используют алиас `@/`, настроенный в TypeScript, Vite и архитектурном ESLint.
- Общие UI-компоненты не зависят от конкретных предметных модулей.
- Циклические зависимости отдельным инструментом пока не проверяются.

Для запуска архитектурной проверки используй `pnpm lint`; полный набор проверок запускается командой `pnpm check`.

## Модули и стили

Функции добавляются вертикально по слоям и группируются по предметной области. Application описывает нужные сценариям порты. Infrastructure реализует эти порты. Presentation содержит UI и взаимодействует со сценариями, не зная об их конкретных технических реализациях.

API DTO и мапперы располагаются рядом с API-адаптером в `src/infrastructure`. Доменные типы и сценарии создаются, когда они нужны интерфейсу или клиентским правилам. Веб-клиент не дублирует серверные бизнес-проверки.

Компоненты, которым нужны собственные стили, хранят CSS Module рядом с компонентом (`*.module.scss`). Не нужно добавлять пустой файл стилей для каждого компонента.

## API и Backend

На текущем этапе API-слой содержит общий транспортный контракт, но не контракты всех backend-сущностей и конечных точек. Успешный ответ представлен обёрткой `{ status, message, data }`.

- `ApiError` описывает HTTP-ошибку и сохраняет HTTP-код, статус Backend, сообщение, `data` и `X-Request-ID`.
- `ApiNetworkError` обозначает сетевой сбой.
- `ApiProtocolError` обозначает ответ, который не соответствует ожидаемому JSON-конверту.

Поля предметных сущностей, схемы запросов, репозитории и конечные точки добавляются отдельно по мере согласования конкретных функций.

Backend отвечает за авторизацию, облачные данные, синхронизацию и серверные бизнес-операции. Операции с Git, SSH, Docker и локальными системными ресурсами не выполняются непосредственно в браузере: для них используются предусмотренные клиентские узлы и защищённые механизмы интеграции.

## Web и Desktop

Application-порт `Platform` описывает окружение и чтение диагностической информации native core. `WebPlatform` сообщает о недоступности native функций. `TauriPlatform` из Infrastructure вызывает только типизированную команду `get_client_info`; выбор адаптера выполняется в `src/app`. React-компоненты не обращаются к Tauri API.

Rust core повторяет те же границы: Domain хранит модель ответа, Application собирает результат, Presentation публикует ограниченную Tauri Command, а `lib.rs` регистрирует команду. Новые системные функции должны проходить через Application-операции и узкие Commands. Подробности запуска и безопасности см. в [руководстве Desktop](desktop.md).
